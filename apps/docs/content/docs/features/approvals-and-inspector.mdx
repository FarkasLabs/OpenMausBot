OpenMausBot renders structured agent events as native conversation cards. Questions, choices, permission requests, tool activity, and failures remain attached to the task that produced them.

## Approval cards

When an engine supports approvals, OpenMausBot surfaces the request instead of hiding it in terminal output. Read the requested action and scope before approving it. Denying an action sends control back to the agent so it can choose a safer path.

## Changes a bot makes to itself

A bot can change its own routines, skills, profile, and default model without asking, at every approval level, including engines such as Pi that have no Full access. Each change shows in the conversation as one plain line, for example "Scout scheduled a routine: Check before dentist, today 2:30 PM", with **Details** for the full text and **Undo** to put it back. After you undo it, the line ends with "Undone". If the thing changed again since, Undo says so and changes nothing.

Outside Full access or YOLO, a change for another bot, such as a Chief editing a teammate's profile or scheduling a routine for it, still asks. Creating, deleting, or moving bots and messages between bots keep their usual approvals. A bot that already has 20 routines on asks before it turns on another one, and a bot asks before it moves its own working folder, since that changes which files its tools can read and write without asking. In a conversation a guest drives on My Cloud, every change still asks.

Full access applies every change as it always has, with the same one-line receipt and Undo.

## YOLO mode

**Settings → General → Workspace YOLO** enables one server-persisted approval policy for existing and future bots, threads, delegated tasks, and unattended routines. Only the workspace owner or admin can enable it. Advanced display mode is not an admin role. On a self-hosted server, sign in as an admin or pair an admin device first. Anonymous loopback access and bot tokens cannot enable it. Read and confirm the destructive-action warning. Stop active turns before changing the setting.

YOLO removes action approvals, including commands and writes outside a bot's working folder. Bots can update their own canonical profile and SOUL through `propose_profile`, manage their own skills, routines and supported settings, and configure their own MCP servers without another approval. Enabled MCP definitions load on the next turn. Account sign-in, genuine questions, selected tools, team access, guest-driven My Cloud boundaries, computer-sharing grants, and operating-system permissions still apply.

Pi supports YOLO through native Full semantics, `--approve`, and `--no-extensions`, while retaining OpenMausBot's explicit MCP extension. Automatic extension discovery is disabled only for YOLO turns. Normal Pi turns keep their existing extension behavior.

Turning workspace YOLO off restores saved bot and thread modes without rewriting them. A separately enabled per-bot YOLO grant still applies to that bot's existing and future threads; choose Ask in its Permissions settings to disable it. Unsupported engines are refused when enabling YOLO. The setting remains effective on an npm/headless server after restart, without a connected desktop. A paired admin can use the responsive web settings from a mobile browser. YOLO is an approval policy, not an operating-system sandbox.

## Inspector

Use **Inspector** when you need more detail than the conversation provides. It is useful for following tool calls, reconnect attempts, engine output, and long-running work.

## When a run disconnects

OpenMausBot retries transient streaming failures. If retries end in an authentication or configuration error, fix the underlying engine rather than repeatedly retrying the task. See [Agent engine troubleshooting](../providers/troubleshooting.mdx).
